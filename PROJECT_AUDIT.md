# Project Audit

**Audit date:** 2026-09-25  
**Scope:** Existing project files and a baseline runtime smoke check. This is a code and workflow audit, not a dataset evaluation.

> Historical snapshot: this audit records the repository state on 2026-09-25. The current app and model state have changed since then; use `README.md`, `docs/EVALUATION.md`, and `reports/ShelfSight_Project_Report.docx` for the packaged current state.

## Executive summary

The repository is a small Streamlit prototype with three Python source files. It can accept a shelf image, propose regions with OpenCV or accept manually entered rectangles, optionally classify crops with a saved Keras model, count classified facings, compare a flat SKU sequence, and download JSON.

The app starts in the current environment and the Streamlit health endpoint responds successfully. The project now includes a synthetic-only 7-class MobileNetV2 SKU demo trained on 35 generated crops. Its training examples are not independent real-world data and no held-out accuracy is claimed. No real labeled shelf dataset or trained RetinaNet shelf detector is included. OpenCV proposal checks establish only that the baseline code path executes; they do not establish real-shelf detection quality or compliance performance.

The first fixes should address the classifier preprocessing mismatch and input validation, then add unit tests around geometry and inventory/compliance behavior before extending the architecture.

## Current architecture and data flow

1. `app.py` collects an uploaded image with Streamlit and converts it to RGB with Pillow.
2. It optionally loads `models/sku_classifier.keras` and `models/labels.json` through `vision.load_classifier`.
3. The app either parses manually supplied rectangles or asks `vision.propose_regions` for OpenCV contour-based candidates.
4. `vision.analyze_shelf` crops each candidate, optionally predicts a SKU, annotates boxes, and counts recognized labels.
5. `vision.make_planogram_report` compares the detected labels with one flat expected sequence.
6. Streamlit displays the annotated image and summary and serializes the result as downloadable JSON.
7. `train.py` loads class-folder images, trains a frozen MobileNetV2 feature extractor with a new softmax head, and saves a Keras model plus class labels.

## Implemented capabilities

- Streamlit upload workflow for JPG, JPEG, PNG, and WEBP file extensions.
- Automatic OpenCV edge/contour region proposals, geometric filtering, overlap-based duplicate suppression, and bounding-box annotations.
- Manual rectangle input as JSON, with normalized or pixel coordinates accepted by the analysis function.
- Optional Keras classifier loading and per-crop top-1 prediction.
- Counts of classified SKU facings; unclassified crops remain in the detection list but are excluded from the inventory table.
- Flat, position-by-position planogram comparison and JSON download.
- MobileNetV2 transfer-learning training entry point with augmentation and early stopping.
- Project-local Python environment and installed runtime dependencies.

## Findings

### Correctness and model handling

1. **Training/inference preprocessing mismatch (high priority).** `train.py` applies `tf.keras.applications.mobilenet_v2.preprocess_input`, which maps image values to the MobileNetV2 input scale. `vision._predict` instead feeds images divided by 255, yielding a different input scale. A model trained by the included script will therefore receive inconsistent inputs at inference.
2. **Duplicate expected SKU facings are not reported correctly as missing.** `make_planogram_report` identifies missing SKUs by membership rather than quantity. For observed `['Cola']` versus expected `['Cola', 'Cola']`, the positions show a missing detection, but the separate `missing` list is empty.
3. **The planogram editor suggests multiple shelf rows, but the implementation flattens them.** Blank lines are removed and there is no shelf/row assignment, geometry grouping, or row-level matching.
4. **Classifier/model metadata is not validated.** Label JSON shape, class count, model output count, input dimensions, and label types are not checked. Load failures are swallowed and presented indistinguishably from an intentionally absent model.
5. **There is no unknown/low-confidence decision policy.** Every classifier output is assigned its top class; the confidence value is shown as a raw softmax score with no configurable threshold, calibration claim, or review status.
6. **Manual rectangle payloads have incomplete schema validation.** Only JSON syntax errors are caught in the UI. Non-list JSON, malformed rows, non-numeric values, non-finite coordinates, and out-of-bounds rectangles can fail or be silently skipped/clipped in the analysis code.
7. **Image decoding and size errors are not handled in the workflow.** Pillow decoding, corrupt content, and exceptional dimensions can interrupt a Streamlit run. Extension filtering is useful but is not content validation or an explicit pixel/dimension limit.
8. **Training does not create a held-out test set or evaluation report.** The built-in split is train/validation only and may place highly similar images from the same source/session on both sides. No class balance report or minimum-per-class check is produced.
9. **Training writes model files relative to the current working directory.** The app loads them relative to its own source directory. Invoking the trainer from another directory can save a model the app does not find.
10. **Reported inventory is recognized-SKU count, not all visible facings or stock on hand.** Unclassified detections are omitted from the inventory table; the UI separately reports total candidate detections. A single shelf image cannot establish back-stock quantity.
11. **Compliance percentage is a simple exact-position score.** It has no configurable rules, widths/spacing, row geometry, tolerance, or uncertain state. It should not be interpreted as a validated operational compliance metric.
12. **No empty-shelf analysis is implemented.** The current code does not identify shelf areas or classify occupied versus empty positions.

### Maintainability, performance, and configuration

- Core functions are all in `vision.py`; the Streamlit UI, vision logic, inventory aggregation, and compliance logic are not separated into modules.
- Type hints are present on only one main function. Most functions lack docstrings, return types, and explicit input contracts.
- Model paths are rooted to `app.py`, while the training output path is current-directory-relative. Image proposal cutoffs, maximum image size, confidence threshold, and training hyperparameters are mostly hardcoded.
- `load_classifier` catches every exception and returns `None`, hiding broken or incompatible model files. There is no application logging for diagnosis.
- Every Streamlit rerun may reload the Keras model and repeat image processing; no resource/data caching is used.
- Contour suppression compares each candidate against retained boxes, which can become costly on highly textured images before the final 100-box cap is applied.
- The app imports `cv2` directly although current UI code does not call it; OpenCV is used in `vision.py` and is still a required dependency overall.
- Dependency declarations are broad lower bounds rather than a tested lock/constraints set. TensorFlow is a large required install even though an untrained/no-model OpenCV-only run is supported.
- `.gitignore` excludes every `*.csv`, which could also hide intentional evaluation/report CSV deliverables. There is no dedicated reports/output policy.

### Security, privacy, and upload handling

- Uploaded image bytes are processed in memory and are not intentionally saved by the app. This is a positive privacy property of the current workflow.
- File type selection is extension-based. Validate decoded content and dimensions and handle decompression/decoder errors explicitly before processing.
- Manual JSON is user-controlled and currently reaches logic with limited structural and numeric validation; validate its schema and coordinate bounds.
- Model and label files are loaded from fixed local paths, not user-entered paths. Preserve that boundary if configurable settings are added.
- There are no secrets or API keys in the reviewed source. `.env.example` is not currently needed for the local-only prototype.

### Documentation and research scope

- The README covers setup, the basic workflow, classifier training, and important limitations.
- It does not document an annotation schema, dataset provenance/licensing, split protocol, evaluation methodology, architecture diagram, or measured results.
- There is no suitable shelf dataset or bounding-box/row/empty-space ground truth in the project. Do not train a detector, report accuracy, or claim empty-space/compliance effectiveness until appropriate annotations and an evaluation set exist.
- The M.Tech research direction in the supplied brief is a proposal only. A literature review and comparisons are still needed before claiming a research gap or contribution.

## Recommended next steps

1. Add unit tests for image validation, coordinate conversion/clipping, deduplication, model preprocessing, SKU counts, and planogram duplicate/missing/unexpected cases.
2. Fix training/inference preprocessing to use one explicit, tested model input contract; validate saved model and labels and report load errors clearly.
3. Add robust upload and manual-box schema validation, dimension limits, and user-facing errors.
4. Separate inventory and planogram logic into small typed modules and make the compliance result distinguish matches, missing quantities, unexpected products, and review-required/unknown observations.
5. Document an annotation format and dataset workflow, then collect/annotate licensed images before training or reporting detection/classification metrics.
6. Add reproducible train/validation/test splits that can group related images to avoid leakage, plus evaluation scripts and measured results only after ground truth exists.
7. Add structured configuration and lock/constraints strategy; keep generated model/data/report artifacts out of source control with specific ignore rules.
8. Revisit the proposed M.Tech question after a literature review and dataset audit; define a baseline and protocol before claiming novelty.

## Scope boundary

This audit adds documentation only. It does not refactor source code, modify model behavior, or claim that the project is production-ready. The Streamlit process was started for the health check and may need to be started again in a later session.
